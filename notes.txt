---------photo storage---------
In production — local disk breaks, for concrete reasons:
- Run two server instances and photos uploaded to server A are invisible to server B.
- Containers have ephemeral disks; a redeploy deletes every photo.
- Your app server ends up spending its time serving image bytes instead of handling API requests.

So production uses an object store — S3, Cloudflaroff of the design: only one file changes. base.py
defines the contract (save, delete, delete_prefix, url_for). You write s3.py implementing those four methods, and get_storage() returns it based on STORAGE_BACKEND. No router, no model, no schema changes — because nothing else ever touched the bytes, only the key.

Two things you'd handle differently in S3:
- url_for() returns a presigned URL — a link that expires in ~15 minutes — rather than a permanent public path. Meal photos are health data; they shouldn't be guessable-and-forever.
- delete_prefix() becomes the "Delete Account" mechanism. That's why the key is meals/{userId}/... — user id first — so wiping one person's photos is deleting one prefix
